Agent Orchestrator runs two distinct types of sessions: an **orchestrator** that supervises the whole fleet, and one or more **workers** that actually write code. Because these roles have very different demands — broad reasoning across many sessions versus fast, focused execution on a single task — you can assign different agents and models to each role. A large model like Opus is a natural fit for the orchestrator; a faster model like Sonnet or Codex keeps worker costs low without sacrificing quality.

## How roles are assigned

You never set the role manually. AO assigns it automatically based on how the session is created:

- `ao start` → creates the **orchestrator** session (named `<prefix>-orchestrator`)
- `ao spawn` (called from the orchestrator) → creates **worker** sessions

AO records a `role` field (`orchestrator` or `worker`) in each session's metadata. The dashboard and lifecycle manager use this to display sessions correctly and to exclude the orchestrator from PR-tracking flows.

## What the orchestrator does

The orchestrator is a long-running supervisor session. Its rules are enforced by the prompt AO injects at startup:

<CardGroup cols={2}>
  <Card title="Read-only by design" icon="eye">
    The orchestrator inspects session status, logs, PR state, and CI output — but never edits files, runs implementation code, or creates its own PR.
  </Card>
  <Card title="Spawns workers via ao spawn" icon="circle-play">
    Passes an issue ID (`#123`, `INT-1234`) or `--claim-pr` to attach an existing PR to a new worker session.
  </Card>
  <Card title="Nudges workers via ao send" icon="paper-plane">
    Sends instructions or clarification directly to a worker's terminal. Always uses `ao send` — never raw `tmux send-keys`.
  </Card>
  <Card title="Monitors via ao status" icon="chart-bar">
    Gets a live view of every session's PR, CI, and review state across all projects.
  </Card>
</CardGroup>

## Global default configuration

Set defaults for both roles under `defaults:` in your `agent-orchestrator.yaml`. These apply to every project unless overridden at the project level.

```yaml
defaults:
  orchestrator:
    agent: claude-code
  worker:
    agent: codex
```

<Note>
  At the global `defaults` level, only the `agent` key is accepted. To configure `agentConfig` options such as `model` or `permissions`, use per-project `orchestrator` and `worker` blocks instead.
</Note>

## Per-project overrides

Project-level blocks accept both `agent` and `agentConfig`, giving you full control over model selection and permissions for each repo:

```yaml
projects:
  myapp:
    repo: org/myapp
    path: ~/code/myapp
    orchestrator:
      agent: claude-code
      agentConfig:
        permissions: permissionless
    worker:
      agent: codex
      agentConfig:
        model: o3
```

<Warning>
  A project-level `orchestrator` or `worker` block **fully replaces** the global default — it is not merged field-by-field. If you set a project-level block, specify every field you need.
</Warning>

## Recipes

<Accordion title="Recipe 1: Opus orchestrator + Sonnet workers">
  Use a large reasoning model to supervise the fleet and a fast model for cost-effective execution:

  ```yaml
  defaults:
    orchestrator:
      agent: claude-code
    worker:
      agent: claude-code

  projects:
    myapp:
      repo: org/myapp
      path: ~/code/myapp
      orchestrator:
        agent: claude-code
        agentConfig:
          model: claude-opus-4
      worker:
        agent: claude-code
        agentConfig:
          model: claude-sonnet-4
  ```
</Accordion>

<Accordion title="Recipe 2: Claude Code orchestrator + Codex workers">
  Keep the orchestrator on Claude Code for tool-heavy coordination and use Codex for cost-effective worker sessions:

  projects:
    myapp:
      repo: org/myapp

## Gotchas

<AccordionGroup>
  <Accordion title="Missing agent binary">
    If you set `defaults.worker.agent: codex` but Codex is not installed, `ao spawn` will fail when a worker session starts. Run `ao doctor` before starting a run to verify all configured agents are available.
  </Accordion>
  <Accordion title="Inheritance replaces, not merges">
    Workers inherit the top-level `defaults` unless overridden at the project level. A project-level block fully replaces the default — it is not merged field-by-field. Specify every field you need in the project-level block.
  </Accordion>
  <Accordion title="Separate rule sets">
    `orchestratorRules` and `agentRules` in the project config apply independently to orchestrator and worker sessions respectively. They are not shared between roles.
  </Accordion>
</AccordionGroup>
