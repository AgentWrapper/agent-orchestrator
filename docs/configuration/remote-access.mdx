By default, the AO dashboard binds to `localhost:3000` and is only accessible from the machine it runs on. This page explains how to reach it from another device — your phone, a second laptop, or a remote server — using Tailscale (recommended), direct network binding, or a reverse proxy with TLS.

<Warning>
  AO has no built-in authentication. Anyone who can reach the HTTP port can view all sessions, read terminal output, send messages to agents, and trigger merges. **Never expose the dashboard port to the public internet** without Tailscale or an authenticating reverse proxy in front of it.
</Warning>

## Tailscale (Recommended)

[Tailscale](https://tailscale.com) creates a private WireGuard mesh network between your devices. Every device gets a stable IP like `100.x.x.x` and a DNS name like `my-laptop.tail1234.ts.net`. No port forwarding or firewall rules are required.

<Steps>
  <Step title="Install Tailscale on both machines">
    Install Tailscale on the machine running AO and on every device you want to access it from.

    ```bash
    # macOS
    brew install --cask tailscale

    # Ubuntu / Debian
    curl -fsSL https://tailscale.com/install.sh | sh
    ```
  </Step>
  <Step title="Authenticate Tailscale">
    ```bash
    sudo tailscale up
    ```
  </Step>
  <Step title="Find your Tailscale IP">
    ```bash
    tailscale ip -4
    # e.g. 100.64.0.1
    ```
  </Step>
  <Step title="Bind AO to all interfaces and start">
    AO binds to `localhost` by default. Set `HOST=0.0.0.0` so Tailscale traffic can reach it:

    ```bash
    HOST=0.0.0.0 ao start
    ```
  </Step>
  <Step title="Access the dashboard from another device">
    Open the dashboard from any device on your Tailnet:

    ```
    http://100.64.0.1:3000
    ```

    Or with MagicDNS enabled:

    ```
    http://my-laptop.tail1234.ts.net:3000
    ```
  </Step>
</Steps>

### Optional: HTTPS via Tailscale Serve

For HTTPS with a valid certificate managed by Tailscale, use `tailscale serve`:

```bash
tailscale serve https:443 / http://localhost:3000
```

This makes the dashboard available at `https://my-laptop.tail1234.ts.net` with a Let's Encrypt certificate. WebSocket connections for the terminal also work through Tailscale serve.

## Binding to a Specific Interface

To make AO reachable on your local network without Tailscale, set the `HOST` environment variable when starting:

```bash
# Bind to all interfaces
HOST=0.0.0.0 ao start

# Bind to a specific IP only (e.g. your Tailscale IP)
HOST=100.64.0.1 ao start
```

To make this permanent, export `HOST` in your shell profile before running `ao start`.

<Note>
  The terminal WebSocket ports (`terminalPort` and `directTerminalPort`) also need to be reachable from remote devices. If you're using Tailscale, the mesh handles this transparently as long as the ports are not firewalled locally.
</Note>

## macOS: Preventing Sleep

If AO runs on a Mac, the machine going to sleep will kill the agents and the dashboard. Use `caffeinate` to prevent sleep while AO is running:

```bash
# Prevent idle sleep only (display sleep is still allowed)
caffeinate -i ao start

# Prevent all sleep including display — for headless overnight runs
caffeinate -dims ao start
```

### Running AO as a Persistent launchd Service

To keep AO running automatically in the background on macOS, create a launchd plist at `~/Library/LaunchAgents/com.ao.orchestrator.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>com.ao.orchestrator</string>
  <key>ProgramArguments</key>
  <array>
    <string>/usr/local/bin/ao</string>
    <string>start</string>
  </array>
  <key>RunAtLoad</key>
  <true/>
  <key>KeepAlive</key>
  <true/>
  <key>EnvironmentVariables</key>
  <dict>
    <key>HOST</key>
    <string>0.0.0.0</string>
  </dict>
</dict>
</plist>
```

Then load the service:

```bash
launchctl load ~/Library/LaunchAgents/com.ao.orchestrator.plist
```

## Reverse Proxy

If you need a domain name with TLS, or want to add HTTP Basic Auth before exposing AO on a shared host, front it with nginx or Caddy.

<Warning>
  AO uses **two WebSocket servers**: one for tmux-attached terminals and one for direct PTY terminals. Your proxy must forward HTTP `Upgrade` headers for both, or the built-in terminal will not work.
</Warning>

### Pinning WebSocket Ports

By default, AO auto-detects available ports starting at 14800/14801. When configuring a reverse proxy, pin the ports explicitly so your proxy config stays consistent:

```yaml
# agent-orchestrator.yaml
port: 3000
terminalPort: 14800
directTerminalPort: 14801
```

Or pass them as environment variables:

```bash
HOST=0.0.0.0 TERMINAL_PORT=14800 DIRECT_TERMINAL_PORT=14801 ao start
```

### nginx

```nginx
server {
  listen 443 ssl;
  server_name ao.example.com;

  # SSL cert config here

  # Dashboard
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }

  # Terminal WebSockets — tmux mux
  location /ws/terminal/ {
    proxy_pass http://127.0.0.1:14800/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 86400;
  }

  # Terminal WebSockets — direct PTY
  location /ws/direct/ {
    proxy_pass http://127.0.0.1:14801/;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 86400;
  }
}
```

Start AO with the matching WebSocket path so the browser client dials through the proxy:

```bash
HOST=0.0.0.0 NEXT_PUBLIC_TERMINAL_WS_PATH=/ws/terminal ao start
```

### Caddy

Caddy handles WebSocket upgrades automatically — no explicit `Upgrade` headers needed:

```
ao.example.com {
  reverse_proxy /ws/terminal/* 127.0.0.1:14800
  reverse_proxy /ws/direct/* 127.0.0.1:14801
  reverse_proxy 127.0.0.1:3000
}
```

Start AO the same way:

```bash
HOST=0.0.0.0 NEXT_PUBLIC_TERMINAL_WS_PATH=/ws/terminal ao start
```

### Proxy Environment Variables

| Variable | Purpose |
|---|---|
| `HOST=0.0.0.0` | Bind the Next.js dashboard to all interfaces |
| `TERMINAL_PORT` | Override the tmux WebSocket server port (server-side) |
| `DIRECT_TERMINAL_PORT` | Override the direct PTY WebSocket server port (server-side) |
| `NEXT_PUBLIC_TERMINAL_WS_PATH` | Override the WebSocket base path the browser dials — required when the proxy rewrites the path |

## Port Reference

| Port | Default | Config key | Env var | Purpose |
|---|---|---|---|---|
| Dashboard HTTP | `3000` | `port` | `PORT` | Next.js app and API routes |
| tmux terminal WS | `14800` | `terminalPort` | `TERMINAL_PORT` | WebSocket for tmux-attached terminal |
| Direct PTY WS | `14801` | `directTerminalPort` | `DIRECT_TERMINAL_PORT` | WebSocket for direct PTY terminal |

<Tip>
  Running multiple AO instances on the same machine? Change all three ports to avoid `EADDRINUSE` errors:

  ```yaml
  # Second AO instance
  port: 3001
  terminalPort: 14810
  directTerminalPort: 14811
  ```
</Tip>

## Mobile Access

The AO dashboard is a responsive web app and works in mobile browsers. Connect over Tailscale and open the URL in Safari or Chrome. The Kanban board and session detail views are usable on a phone screen.

**Limitations on mobile:** the built-in terminal (xterm.js) works but is difficult to type in on a touchscreen. Use it to read agent output; for sending messages, use the session detail input field. There is no native mobile app or push notification support.

## Security Considerations

<CardGroup cols={2}>
  <Card title="Use Tailscale" icon="shield-check">
    The Tailscale mesh is authenticated and encrypted end-to-end. Only devices on your Tailnet can reach the IP — no additional auth layer needed.
  </Card>
  <Card title="HTTP Basic Auth" icon="lock">
    If you must use a public host, put nginx or Caddy with HTTP Basic Auth in front of AO. Do not expose the dashboard port directly to the internet.
  </Card>
</CardGroup>

<Warning>
  Environment variables and secrets in agent processes are visible to anyone with dashboard access. Do not run AO on a shared machine without Tailscale or authentication.

  If you expose the dashboard publicly and have a webhook configured, the `/api/webhooks` endpoint receives push events from GitHub. Verify your webhook secret (`secretEnvVar`) is set before exposing the port publicly.
</Warning>

You can also firewall at the OS level to allow only Tailscale traffic:

```bash
# UFW example — allow only Tailscale interface
sudo ufw allow in on tailscale0 to any port 3000
sudo ufw deny 3000
```
