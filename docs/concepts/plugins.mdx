Everything in Agent Orchestrator is a plugin. The default setup — Claude Code, tmux, git worktrees, GitHub for issues and PRs, desktop notifications, iTerm2 — works out of the box for common GitHub workflows. When your setup is different, you swap the relevant plugin rather than reconfiguring the whole system. Eight named slots cover every moving part of the agent execution lifecycle, from where the code is checked out to where you get notified when a session needs attention.

## The 8 Plugin Slots

Only one plugin is active per slot at a time. Seven slots are pluggable at runtime; the Lifecycle slot is built into core and cannot be replaced — it is the state machine, poll loop, and reaction engine that connects all other plugins.

| Slot | Available plugins | Default |
|---|---|---|
| **Agent** | claude-code, codex, cursor, opencode, aider, + 18 more | `claude-code` |
| **Runtime** | tmux, process | `tmux` (macOS/Linux), `process` (Windows) |
| **Workspace** | worktree, clone | `worktree` |
| **Tracker** | github, gitlab, linear | `github` |
| **SCM** | github, gitlab | `github` |
| **Notifier** | desktop, slack, discord, webhook, composio, openclaw, dashboard | `desktop` |
| **Terminal** | iterm2, web | `iterm2` (macOS) |
| **Lifecycle** | core (built-in, non-pluggable) | — |

## Runtimes

The Runtime slot controls where agent processes execute. It determines how sessions are created, attached to, and cleaned up.

<CardGroup cols={2}>
  <Card title="tmux" icon="terminal" href="/plugins/runtimes/tmux">
    Default on macOS and Linux. Each agent gets its own tmux window you can attach to directly. Sessions survive terminal disconnects and daemon restarts.
  </Card>
  <Card title="process" icon="microchip" href="/plugins/runtimes/process">
    Cross-platform child-process runtime. Required on Windows. No tmux dependency — sessions run as managed child processes of the AO daemon.
  </Card>
</CardGroup>

## Workspaces

The Workspace slot controls how code is isolated for each session. Each session always gets its own checkout — the question is how that checkout is created.

<CardGroup cols={2}>
  <Card title="worktree" icon="code-branch" href="/plugins/workspaces/worktree">
    Git worktree per session. Fast — shares the object database with your main checkout. Recommended for most setups.
  </Card>
  <Card title="clone" icon="copy" href="/plugins/workspaces/clone">
    Full repository clone per session. Use when your tooling doesn't work correctly with a shared `.git` directory.
  </Card>
</CardGroup>

## SCM

The SCM slot controls how AO reads PR state, CI results, review decisions, and merge readiness. It is separate from the Tracker slot — a project can use GitHub for issues and GitLab for SCM if needed.

<CardGroup cols={2}>
  <Card title="GitHub" icon="github" href="/plugins/scm/github">
    PRs, reviews, and CI status via the `gh` CLI and GitHub's GraphQL API.
  </Card>
  <Card title="GitLab" icon="gitlab" href="/plugins/scm/gitlab">
    Merge requests, discussions, and pipeline status via `glab`.
  </Card>
</CardGroup>

## Notifiers

The Notifier slot controls where AO sends updates when sessions change status. You can configure multiple notifiers — for example, `desktop` for immediate local alerts and `slack` for team-wide visibility.

## Plugin Loading Order

When AO resolves a plugin name, it searches in this order and uses the first match:

1. **Bundled plugins** — shipped with the AO desktop app or npm package
2. **Registry / npm** — packages installed via `ao plugin install` or found in `node_modules`
3. **Local path** — a relative or absolute filesystem path in `agent-orchestrator.yaml`
4. **Inline shortcut** — a short name alias defined directly in the config

## Managing Plugins

### List installed plugins

```bash
ao plugin list
```

### Install a plugin from the registry

```bash
ao plugin install <plugin-name>
```

## Creating a Plugin

Every plugin is a small Node package that exports a `manifest` object and a `create()` function. The fastest path to a working plugin is the scaffold command:

```bash
ao plugin create --slot notifier --name pagerduty
```

This generates a starter package in the current directory with the correct manifest structure, TypeScript types, and example `create()` implementation for the specified slot. From there you fill in the integration logic and reference the local path in `agent-orchestrator.yaml`.

<Tip>
  The scaffold command works for all seven pluggable slots. Pass `--slot agent`, `--slot runtime`, `--slot workspace`, `--slot tracker`, `--slot scm`, `--slot notifier`, or `--slot terminal` to generate the right starter template.
</Tip>
